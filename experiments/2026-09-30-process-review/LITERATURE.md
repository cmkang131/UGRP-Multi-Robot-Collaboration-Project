# UGRP 연구 절차 단축: 문헌·실무 조사와 v2 제안

작성: 2026-09-30, Codex. **제안 문서이며 현재 규칙을 바꾸거나 실행을 승인하지 않는다.** 조사 기준 소스는 `a8094cc14e098a55483f53a3c49bf6a0b116043d`(main, #291 병합)다. 작업 범위는 문헌 조사·정적 파일 확인·문서 작성이다. 물리·시뮬레이션·렌더링·추가 모델 호출은 하지 않았다. 이 문서는 실험 성능 결과가 아니므로 TensorBoard 변환 대상이 아니다.

## 1. 먼저 바꿀 것

**확증의 엄격함은 유지하고, 탐색 중 되풀이하는 문서·검토·이관을 줄이는 편이 먼저다.** 사전 등록은 결과를 보기 전의 약속을 남기는 방법이다. 매 개발 패치마다 학술지의 사전 심사와 같은 절차를 거쳐야 한다는 뜻은 아니다. 짧은 등록도 가능하지만 가설·표본·분석·중단 규칙은 생략할 수 없다. [M01–M04]

우선순위는 다음과 같다. 분 단위 절감은 **UGRP 실측이 아닌 도입 후 확인할 가정**이며 서로 겹치므로 더하지 않는다. 위험은 잘못된 과학적 결론이나 검증 누락의 위험이다.

| 순위: 절감 시간 / 위험 | 구체적 변경 | 대체할 현재 작업 | 예상 효과와 위험 |
|---|---|---|---|
| 1 | 한 후보의 코드·등록 차이·검사 결과를 한 묶음으로 만들고, 독립 검토와 알려진 사례 인수 확인을 병렬 진행 | 여러 문서 사이의 재질문, 검토가 끝나야 시작하는 모든 인수 작업 | 예시에서 두 20분 작업은 40→20분. 독립 작업만 겹치면 위험 낮음. 최종 수정 뒤 관련 검사를 다시 해야 함 |
| 2 | 공통 연구 계약 + 후보별 짧은 등록 + 자동 manifest·변경표 | 같은 입력 경계·판정·환경·pin 목록을 후보마다 수기로 복제 | 예시에서 문서·봉인 35→5–10분. 생성기 오류 위험 중간; 초기에 구형 검사와 교차 검증 |
| 3 | 위험 등급별 검토, 동일 결함의 재검토는 수정 범위와 영향 경로 중심 | 오탈자·기계 생성 파일에도 전체 xhigh 검토를 반복 | 후보당 검토 1회분 이상을 줄일 가능성. 과소 분류 위험 중간; 제어·평가·입력 경계는 독립 검토 유지 |
| 4 | 작업 중인 후보(WIP) 제한, 짧은 브랜치, 기본 OFF 후보를 한 구현 경로로 개발 | 탐색용 monkey patch를 등록용 코드로 다시 이식하고 여러 브랜치에서 재봉인 | 대기·충돌·중복 구현 감소. 절감 분량 미측정. OFF 경로 오염과 미검증 후보 사용 위험 중간 |
| 5 | 문서 전용 CI 경로 → 보수적 변경 영향 선별 → 필요할 때 병합 큐 | 모든 변경의 전체 job 실행, 같은 통합 검사의 반복 | 선택되는 job·대기량에 따라 달라짐. 의존성 누락 위험 중간~높음; 현재 전체 검사 제거부터 하지 않음 |
| 6 | 사전에 정한 실패 확정 조기 종료 → 필요할 때 집단 순차 검정 | 결론이 이미 실패로 확정된 표본을 끝까지 실행 | 60건 중 20건에서 실패 확정이면 남은 40건을 생략할 수 있음. 성공 조기 종료·적응 설계는 통계 검토 비용과 위험이 더 큼 |

## 3. 연구 방법: 빠른 탐색과 정직한 확증

### 3.1 등록을 짧게 만들되 약속은 구체적으로

| 주제·근거 | UGRP에 맞는 1–3개 실천 | 대체할 절차 | 위험·경계 |
|---|---|---|---|
| 짧은 사전 등록(preregistration lite), 사전 심사(Registered Reports) [M01–M03] | 공통 계약을 한 번 검토하고 후보 문서에는 바뀐 가설·구성·표본·판정만 쓴다. 등록 문서는 단일 JSON에서 사람이 읽는 표와 함께 생성한다. 후보 선택이 끝난 뒤 확증 자료를 열기 전에 고정한다 | 개발 패치마다 긴 등록 문서를 새로 쓰고 같은 공통 규칙을 재심사 | lite는 길이의 축소다. 핵심 분석을 비워 놓는 방법이 아니다. 내부 등록은 학술지의 사전 게재 승인(IPA)이 아니다 |
| 계획 변경·일탈(deviation) 보고 [M04] | 변경 시각·이유·당시 본 자료·영향받는 주장·후속 조치를 한 행에 남긴다. 결과를 본 뒤의 새 분석은 탐색으로 표시한다. 실행 전의 실질 변경은 새 등록과 새 해시로 고정한다 | 수정마다 옛 문서를 다시 쓰거나, 사소한 오류 때문에 전체 연구를 폐기 | 원본 등록과 실패는 보존한다. 변경 공개는 결과를 사전 예측으로 소급 바꾸는 허가가 아니다 |
| 탐색→확증과 보류 자료(holdout) [M01, M12, M14] | `dev`·알려진 `acceptance`·미개봉 `confirmatory`를 분리한다. 배치/지도 가족 단위로 분리하고 PF·모델 seed를 별도 기록한다. 최종 후보 선택 후 한 번 확증하고, 결과를 본 후 튜닝하면 새 연구 라운드로 남긴다 | 같은 사례·seed를 고친 뒤 다시 “held-out 통과”로 부르는 반복 | seed 숫자가 다르다고 독립 과제가 되지 않는다. 같은 test를 반복 질의하면 선택 편향이 생긴다. 새 test를 매번 받아 통과할 때까지 도는 것도 연구 질문 전체의 다중 시도다 |

후보별 등록의 최소 내용은 다음 **8묶음**으로 제안한다(문헌의 보편적 8항목 표준이라는 뜻은 아니다).

1. 연구 질문·주요 비교 1개·최소 의미 차이·주장의 범위(단계 probe/연쇄/E2E).
2. 후보·기준선의 실행 manifest 해시, 코드 commit, 입력/정답 경계, 물리·센서·모델·환경.
3. dev/acceptance/confirmatory 분리 기준, 이미 열어 본 자료와 후보 선택 이력.
4. 독립 표본 단위·배치/지도 층·seed·조건 순서·쌍짓기·최대 N과 N의 근거.
5. 성공·시간·명령 수·호출·비용, 실패/타임아웃/결측의 처리와 분석 코드 해시.
6. 주요 가설 검정 또는 추정 방식, 다중 비교·반복 확인 보정, 사전 중단 규칙.
7. HOST_ERROR(ENOSPC 포함)·재시도·제외 규칙·원본 보존 위치와 해시.
8. 독립 검토 receipt, 확증 시작 시각, 일탈 기록, 결과가 실패여도 보고할 항목.

모집단 추론을 원하지 않는 정해진 유한 격자의 공학적 인수 기준이면 그렇게 명시한다. “주어진 60개 배치 중 48개 통과”와 “새 배치 성공 확률이 80% 이상”은 서로 다른 주장이다.

### 3.2 조기 종료와 적응 설계: 복잡도를 단계적으로 올린다

| 방법·근거 | 구체적 적용 | 대체할 절차 | 위험·도입 판단 |
|---|---|---|---|
| 실패 확정 종료(curtailment) [M05의 개념을 유한 인수 격자에 적용] | 사전에 N=60, 최소 성공 48로 정했다면 13번째 실패부터 성공 상한이 47이므로 중단. 실제 실행 수·성공 수·미실행 수를 모두 보고 | 합격이 수학적으로 불가능해도 60건을 채우는 실행 | 가장 단순한 첫 후보. 미실행을 관측 실패로 채워 47/60 같은 성능 추정치를 만들지 않는다. 조기 합격은 별도로 허용하지 않음 |
| 집단 순차 검정(group-sequential), 알파 지출(alpha spending) [M05] | 주요 비교 하나에 중간 확인 시점과 Nmax를 미리 정한다. 간단한 보수적 출발점은 3회 확인 각각 α=0.05/3. 더 효율적인 Pocock/O’Brien–Fleming 계열은 해당 통계량·정보량에 맞춰 설계한다 | 매 배치가 끝날 때 보정 없이 p<0.05를 확인하거나 언제나 최대 N 실행 | 유효한 고정 시점 p값과 사전 표본 설계가 전제. 이진·쌍지은·군집 자료에 정규 평균용 경계를 그대로 쓰지 않는다. 작은 N에서 절감이 없거나 최대 N이 늘 수 있음 |
| 적응 설계(adaptive design) [M06] | dev 단계에서 약한 후보를 빨리 중단. 확증 단계의 분산 기반 표본 수 재추정·군 중단은 사용 정보와 규칙을 먼저 정의하고 통계 전문가가 확인한 경우에만 적용 | 모든 후보를 똑같은 큰 코호트로 평가 | 지금은 dev에서만 사용 권고. 결과를 보고 유리한 배치만 더 뽑으면 비교 대상과 추정량이 바뀐다. 임상 규제 절차를 로봇 연구에 도입하자는 뜻은 아님 |
| 베이지안 순차 종료(Bayesian sequential stopping) [M07] | 사전분포·우도·의사결정 손실·최대 예산을 먼저 정하고, 예를 들어 P(성공확률>목표\|자료)의 경계를 사용. 사전분포 민감도와 판정 특성을 별도 평가 | 임의의 “충분히 잘 됐다” 중단 | 사후확률 95%는 자동으로 빈도주의 1종 오류 5%가 아니다. 기본 사전분포·정지 규칙·자료 선택에 따라 보장이 달라져 초기 v2 기본값으로는 비권고 |
| 시간 전체에 유효한 구간(confidence sequence) [M15] | 자주 보아야 하는 지표에 가정이 맞는 구간을 선택하고, 미리 정한 의미 차이 경계와 비교 | 매번 보통 95% 신뢰구간을 새로 계산해 유리할 때 중단 | 편리하지만 작은 N에서 넓을 수 있다. 군집·비독립 자료 및 여러 후보 선택 문제까지 자동 해결하지 않음 |

세 번의 유효한 검정에 각각 0.05/3을 쓰면 합집합 상한으로 전체 1종 오류가 최대 0.05다. 이것은 **설명용 보수적 계산**이며 현재 UGRP 72건 계획을 바꾸는 검정 설계가 아니다. 주요 비교가 여러 개면 그 비교 사이에도 오류 예산을 배분해야 한다. 중간 결과는 작성자에게 디버깅용으로 공개하지 않고 조정자가 예정된 continue/stop만 집행하는 편이 좋다. 소스를 고칠 필요가 생기면 코호트를 실패/중단으로 보존하고 다시 탐색으로 돌아간다.

“첫 20건 안에 13번 실패”라는 가정에서는 남은 40/60=66.7%의 실행을 줄인다. 실제 평균 절감은 실패율·순서·실행별 시간에 달려 있으며 이번에 측정하지 않았다. 조기 종료 후 전체 성능 구간을 보고하려면 종료 규칙을 반영해야 한다.

### 3.3 로봇·RL 평가와 민감도 보고

| 주제·근거 | UGRP에 맞는 1–3개 실천 | 대체할 절차 | 위험·경계 |
|---|---|---|---|
| seed·구현·분산 [M09, M11, M12] | 성공률만 아니라 효과 크기·불확실성·실패 유형을 보고한다. dev 분산과 최소 의미 차이로 N을 정한다. 비교 조건에 같은 배치 목록을 쓰고 조건 실행 순서를 균형화한다 | “3/5 seed면 충분”, 가장 잘 된 seed 선택, 일괄 큰 N | 같은 배치의 여러 프레임·두 로봇·동일 출력 seed를 독립 표본으로 세지 않는다. 가능한 경우 배치별 쌍지은 차이를 분석하고 환경 층을 유지한다 |
| 적은 실행의 요약 [M10] | 연속 점수의 여러 과제 비교에는 IQM·성능 프로파일·계층/층화 bootstrap을 검토한다. 성공 이진값은 분모와 적절한 구간, 시간은 실패·검열 처리와 함께 제시한다 | 평균 하나로 순위를 확정하고 애매한 결과마다 검토자를 늘리는 관행 | rliable는 작은 표본을 큰 표본으로 만들지 않는다. UGRP 이진·군집 구조에 논문의 집계를 무조건 적용하지 않음 |
| 로봇 benchmark 분리 [M13] | 알려진 과제의 새 초기 상태와 보지 못한 과제/지도를 구분한다. 단계 probe→연쇄→E2E에 서로 다른 판정표를 둔다. sim-to-real은 별도 물리 환경·카메라·하중 검증으로 둔다 | GT staging 성공을 E2E로 승계, 새 seed를 새 지도 일반화로 표현 | Meta-World의 50개 조작 과제 수를 UGRP 필수 표본 수로 가져오지 않는다. 시뮬레이션 운반 성공은 실물 성공 근거가 아님 |
| 다중 분석·강건성(multiverse/robustness) [M08] | 결과를 보기 전에 타당한 소수의 분석 선택을 정하고 모두 표로 내보낸다. 예: 주 분석+HOST_ERROR 포함 민감도, 배치 가족별 결과, 주 시간 요약+타임아웃 포함 요약 | 같은 결론을 여러 에이전트가 문장으로 반복 재검토 | 유리한 분석을 주 분석으로 바꾸지 않는다. 통계적 다중성은 따로 처리. **새 제어 임계값·평가 의미·GT 경계 변경의 코드 검토를 대체하지 않는다** |

문헌이 직접 다루는 multiverse는 주로 자료 처리·분석 선택이다. 제어기 임계값 조합을 모두 실행하는 것은 별도의 탐색 실험이며, 그중 최고값을 같은 자료의 확증 결과로 삼으면 안 된다. 프레임 재생의 반사실 분석도 실제 폐루프 성능과 구분한다.

## 4. 코드·절차 관리: 고정할 것은 실행, 바꿀 수 있는 것은 개발

### 4.1 작은 변경과 대기열

| 주제·근거 | UGRP에 맞는 1–3개 실천 | 대체할 절차 | 위험·경계 |
|---|---|---|---|
| 짧은 브랜치·작은 배치(trunk-based development) [E01, E02] | 한 연구 가설을 한 작은 PR로 만들고 같은 후보의 수정은 같은 PR에서 끝낸다. 구현은 기본 OFF로 일찍 통합하고, 코호트는 검증한 commit에서 실행한다. 탐색/확증 상태는 run metadata로 구분한다 | 미세 변형마다 장기 branch·worktree·PR을 만들고 탐색 코드를 등록 코드로 복사 | 짧은 branch는 소스 고정 폐기가 아니다. 실행 worktree는 코호트 동안 불변. default-OFF 통합도 독립 코드 검토를 거치며 성능 채택과 구분 |
| 진행 중 작업 제한(WIP), 제약 이론(TOC), Little의 법칙 [E04–E06] | 사람/조정자의 검토·봉인·물리 슬롯 중 가장 긴 대기를 먼저 잰다. 시작값으로 구현 후보 2개·독립 검토 1개·물리 슬롯 1개를 제안한다. 막힌 후보가 있으면 새 구현보다 검토·증거 정리를 먼저 처리한다 | 에이전트가 비는 즉시 새 후보를 열어 검토 대기만 늘리는 방식 | 2/1/1은 UGRP용 가설이지 문헌 최적값이 아니다. 실제 처리량을 유지할 만큼의 준비 작업은 필요하다. 물리·훈련 잠금은 계속 존중 |
| 흐름 지표(DORA를 연구에 맞게 변형) [E03] | 첫 변경 시작→확증 결론의 경과시간, review ready→첫 응답, 마지막 수정→seal, seal→첫 run, run→보고를 기록한다. 코드 결함에 의한 재작업 비율·무효 코호트 비율도 함께 본다 | 커밋 수·PR 수·모델 토큰 속도를 생산성으로 간주 | DORA 원래 change lead time은 commit→production, change fail rate는 배포 후 개입 비율이다. 연구에서 가설이 실패한 비율은 코드 변경 실패율이 아니다 |

Little의 법칙은 안정된 흐름에서 `평균 WIP = 처리량 × 평균 체류시간`이다. 예를 들어 처리량이 하루 2개로 유지된다면 WIP 6개는 평균 3일, 2개는 평균 1일이다. **이 숫자는 산술 예시이며 UGRP 관측치나 WIP를 줄이면 무조건 3배 빨라진다는 인과 추정이 아니다.** 검토가 병목이면 코드 생성만 빠르게 해도 전체 완료 시간은 크게 줄지 않는다.

### 4.2 위험별 검토와 CI

아래 등급은 **제안**이다. 현재 [AGENTS](../../AGENTS.md)의 독립 검토·소유자 승인·CI 의무는 별도 정책 변경이 채택되기 전까지 그대로 적용한다. Google의 빠른 검토 지침은 사소한 의견 때문에 다음 응답까지 기다리는 비용을 줄일 근거이며, 아래 등급표 자체를 검증한 실험은 아니다. [E07]

| 등급 | 예시 | 제안하는 필수 확인(gate) | 반복하지 않을 것 |
|---|---|---|---|
| R0: 의미 불변 기록 | 오탈자, 링크, 기존 값을 그대로 내보낸 표 | 문서 검사·원본 대조·소유자 절차. 분석 의미가 바뀌면 R2 | 제어기 전체 xhigh 재검토·물리 replay |
| R1: 개발 보조·격리 도구 | 정적 검사기, 개발 전용 보고 생성기 | 영향 테스트와 범위 검토. 결과 분류·삭제·실행 경로에 닿으면 R2 | 무관한 연구 가설의 재심사 |
| R2: 제어·평가·등록 계약 | 제어 수십 줄, 입력·가드·시드/분모·성공 정의·소스 closure | 작성자와 별개의 검토자 1명이 최종 diff·계약·반례를 검토. 영향 테스트, 필요한 인수, 정확한 해시를 확인 | 동일한 계약을 여러 모델이 차례로 처음부터 읽기. 스타일 의견만으로 전체 재검토 |
| R3: 비가역/권한 변경 | raw 삭제·덮어쓰기, 연구 경계 완화, 예산·권한 확대 | 현재의 명시적 사용자 결정 및 독립 검토 | 승인 자동화나 “작은 diff”에 의한 낮은 등급 처리 |

독립 검토 1회란 결함을 고치지 않고 한 번 읽고 끝낸다는 뜻이 아니다. 검토자는 처음에 **모든 blocking 지적과 반례를 모아서** 전달한다. 수정 후에는 변경된 부분과 전이 영향 경로를 다시 본다. 통계 가정·입력·심판·물리가 달라지면 전체 관련 계약을 다시 검토한다. P2 문체 의견은 후속 작업으로 명시적으로 해소하고, 현재 미해결 리뷰 대화를 무시해 병합하지 않는다. 리뷰 횟수나 시간 제한이 승인 근거가 될 수는 없다.

CI는 다음 순서가 적합하다. [E08–E10]

1. **R0 문서 전용 경로부터**: 문서 파일뿐 아니라 실행기가 읽는 Markdown/JSON·등록 파일이 섞였는지 검사한다. 문서 검사가 성공했고 실행 의존성과 교집합이 없다는 근거를 항상 실행되는 집계 check에 남긴다.
2. **보수적 영향 선별(test impact analysis)**: 변경 경로에서 역의존성·fixture·설정·공통 경계를 확장한다. CI/의존성/장면/공통 제어/평가/manifest 생성기 변경은 전체 관련 suite로 확장하고 모르는 경로는 전체 실행한다. 초기에 선별 결과와 전체 결과를 함께 비교해 놓친 실패를 센다. 지금 당장 ML 선별기를 도입할 이유는 약하다.
3. **병합 큐(merge queue)는 충돌 비용이 클 때**: 최신 base와 앞선 PR을 합친 상태를 검증한다. `merge_group` 이벤트·required check 집계·플랜 제공 여부를 먼저 확인한다. 현재 자동 병합 예약 금지와 다른 자동화이므로 정책을 명시적으로 정리한 뒤 도입해야 한다. 이 조사에서는 켜지 않는다.

GitHub는 workflow 전체를 경로/commit 필터로 건너뛰면 required check가 Pending에 남을 수 있다고 설명한다. “실행 안 됨”을 성공으로 뭉개지 말고, 필요한 job 목록을 계산한 뒤 그 목록의 성공을 집계해야 한다. 현재 fail/cancel/skip을 거절하는 집계기를 임의로 약화하지 않는다. 전체 통합 검사는 cohort 진입에 필요한 범위에서 유지하고, 연구용 모델 호출이나 물리 실행을 단순 문서 변경에 새로 연결하지 않는다.

### 4.3 해시·구성·실험 등록부

| 주제·근거 | UGRP에 맞는 1–3개 실천 | 대체할 절차 | 위험·경계 |
|---|---|---|---|
| 내용 주소형 식별(content addressing), 격리 빌드(hermetic build) [E11, E12] | 실행에 영향을 주는 코드·구성·도구·환경·자산·명령을 자동 manifest로 고정한다. 전체 Git SHA는 출처로 함께 저장한다. 변하지 않은 결정적 정적 검사의 결과만 해당 입력 해시로 재사용한다 | 수동 pin 추가와 파일명/번호만을 근거로 한 재봉인 | Python 동적 import·subprocess·자료 로딩·native library를 AST만으로 완전히 찾을 수 없다. 더 적은 파일 수보다 누락 없는 경계가 우선 |
| 실행 식별과 관리 번호 분리 [E11, E13에서 도출] | stable workflow는 실행 API/계약 버전으로, 후보는 구성+의존성 digest로 식별한다. 과거 v83 같은 이름은 불변 alias로 남긴다. 후보 선택 전 dev run은 commit+config hash+고유 run ID로 남긴다 | 모든 변형에 bundle/workflow/revision 번호를 함께 올리고 전 branch 최대값을 예약 | 현재 규칙을 바꾸는 migration이 필요. 동일 의미라는 이유로 다른 해시를 합치거나 과거 성공을 승계하지 않음 |
| 실험 등록부(registry) [E13–E16] | 기존 `sim_cli` manifest에 phase·parent·hypothesis·candidate hash·split hash·review/seal receipt·결과 해시를 더한다. README/PR/TensorBoard 메타데이터는 여기서 만든다. raw는 기존 위치와 해시로 참조한다 | 여러 Markdown/JSON에 상태와 숫자를 복사 | 별도 서버·대시보드를 늘리지 않는다. append-only 이력과 변경 사유가 필요하며 tracking 도구가 사전 등록·독립성을 자동 보장하지 않음 |
| 기능 스위치·숨은 배포(feature flags, dark launch) [E02] | 선택하지 않으면 기존 경로가 유지되는 OFF 후보를 같은 코드로 dev/확증에 사용한다. 선택 값은 실행 manifest에 고정한다. 주인이 있는 만료/정리 계획을 둔다 | 탐색 monkey patch→등록 구현 이식→동등성 재검증 반복 | import 부작용과 조합 폭발을 검사한다. 로봇 제어의 dark launch는 실제 명령을 몰래 실행하는 것이 아니라 코드 통합 후 미선택 상태를 뜻한다 |

권장 키의 개념은 아래와 같다. 아직 구현된 schema나 호출 명령이 아니다.

```text
execution_digest = H(실행 closure + canonical config + 장면/물리/카메라/모델/지도
                     + 환경/도구 버전 + 명령·관측 타이밍 + 입력 데이터)
study_digest     = H(execution_digest + 비교군 manifest + split/표본/분석 계획
                     + 심판/분류기/분석 코드 + 중단/예외 규칙)
run_id           = 고유 실행 ID            # 같은 digest를 여러 번 실행할 수 있음
provenance       = 전체 Git SHA + tree 상태 + 원본 위치/해시 + review/seal receipt
```

manifest 자체의 해시를 자기 입력에 넣는 순환은 피하고, 실행 payload의 digest를 별도 봉인 문서가 참조하도록 한다. 문서 변경 commit과 실행 source commit을 명시적으로 분리할 수는 있지만 실제 실행 source가 봉인과 맞는지 매번 검사한다. 현재 HEAD 일치 검사를 그냥 끄는 제안이 아니다.

**파일 268개가 정말 전이 의존성이면 268개를 그대로 해시한다.** 목표는 해시 계산을 몇 밀리초 줄이는 것이 아니라, 변경이 무관한지 사람이 증명하고 여러 문서를 다시 쓰는 비용을 없애는 것이다. 의존성 축소는 모듈 분리와 명시적 실행 진입점으로 한다. “이번 trace에서 안 읽혔다”만으로 다음 분기의 파일을 빼지 않는다. 핵심 소스·설정·동적 자산을 하나씩 변조했을 때 키와 검사가 바뀌는 검증이 선행돼야 한다.

| 도구 | 가져올 관행 | 이번 규모에서의 선택 |
|---|---|---|
| DVC | stage의 명령·deps·params·산출물 hash/lock | 기존 runner의 manifest 생성에 활용할 개념. DVC가 Python 의존성을 자동으로 완전히 찾는다고 가정하지 않음 |
| MLflow | run별 매개변수·지표·artifact·parent 관계와 검색 | 서버 이전보다 기존 JSON 등록부의 공통 필드부터. 현재 TensorBoard 보기는 유지 |
| Sacred | 실행 당시 config·source·dependency·seed 수집 | 실행 전후 provenance 수집의 참고. 자동 수집 범위 밖 자산을 별도로 명시 |
| Hydra | 구성 조합과 multirun 분리 | 작은 구성 공간을 먼저 선언. 기본 launcher의 실행을 무제한 병렬화하거나 새 물리 슬롯을 만드는 도구로 쓰지 않음 |
| Bazel | action의 선언 입력과 content-addressed cache | 전체 저장소 이관보다 결정적 정적 검증 cache부터. 물리 결과·새 표본·모델 응답은 cache hit를 새 실행으로 세지 않음 |

## 5. AI 에이전트: 호출 수보다 완료까지 걸린 시간

| 주제·근거 | UGRP에 맞는 1–3개 실천 | 대체할 절차 | 위험·경계 |
|---|---|---|---|
| 독립 작업 병렬화 [A01, A02] | 같은 후보 SHA에 대해 코드 독립 검토와 계약/자료 감사, 이미 준비한 인수 실행을 겹친다. 파일 소유자와 출력 형식을 먼저 정한다. 직렬 의존 작업에는 추가 에이전트를 붙이지 않는다 | 리뷰→설명 요청→인수 준비→등록 초안의 연속 대기 | 같은 파일을 동시에 수정하면 재작업이 늘어난다. 동일 모델 여러 개의 동의가 통계적 독립 증거는 아니다. 공용 Mac에서 CI와 물리 부하를 겹치는 것도 금지 |
| 먼저 짧게 계획하고 실행(plan-then-execute) [A03, A04] | 5–10줄 변경 계약에 가설·허용 파일·입력 경계·금지 동작·검사·완료 기준을 쓴다. 구현자 1명, 별도 검토자 1명, 조정자 1명으로 책임을 나눈다 | 매 세션이 전체 문서를 재탐색하고 계획을 다시 쓰기 | 작은 패치에 다단계 spec 승인 파일을 더 만들면 오히려 느려진다. spec-driven development에서 가져올 것은 검사 가능한 계약이지 문서 수가 아님 |
| 모델·추론 강도 라우팅 [A01] | 형식 변환·링크·hash·등록부 생성은 스크립트로 한다. 정해진 계약의 단순 수정은 검증 가능한 빠른 모델/보통 effort 후보로, 통계·GT 경계·새 제어 의미는 강한 모델의 독립 검토로 보낸다 | 모든 읽기·복사·보고에 xhigh 호출 | 빠른 모델이 항상 더 싼 총 작업을 만드는 것은 아니다. 실패·재작업까지 측정하고 계약을 벗어나면 즉시 상향. 현재 전역 모델 설정은 변경하지 않음 |
| 체크리스트와 자동 검증기 [A03, E07] | 리뷰 입력을 diff·실패 반례·테스트 receipt·계약 diff로 제한한다. 출력은 P0/P1/P2·정확한 위치·반례·판정으로 고정한다. JSON schema/해시/seed 중복/GT 경로 같은 기계 판정은 코드에 맡긴다 | 여러 모델의 길고 유사한 자유 서술 검토와 재확인 | 검증기는 자신이 모델링하지 않은 오류를 놓친다. 주장이 바뀌는 과학적 검토는 남기고 LLM의 “통과” 문장을 테스트 결과로 취급하지 않음 |

Anthropic의 2025 연구 시스템 글은 병렬화로 복잡한 조사 시간이 **최대 90% 감소**했다고 보고하지만, 다중 에이전트가 일반 채팅 대비 약 **15배 토큰**을 쓰며 강하게 결합된 코드 작업은 병렬화하기 어렵다고도 적는다. 제품팀 내부 사례이며 UGRP 예상 개선율로 사용하지 않는다. [A02]

반대 근거도 있다. METR의 2025 무작위 실험은 숙련 개발자 **16명·246개 과제**에서 당시 AI 사용 시 시간이 **19% 증가**했다고 보고했다. 2026 후속 글은 선택 편향과 동시 에이전트의 시간 측정 문제 때문에 최신 속도 향상의 크기를 신뢰하기 어렵다고 설명한다. 따라서 “AI는 19% 느리다”나 “병렬 agent면 90% 빠르다”를 지금의 작업에 일반화하지 않는다. [A05, A06]

## 6. v2 작업 흐름 제안

아래는 **향후 채택할 절차**다. 이번 조사에서 에이전트·물리 실행을 추가하지 않는다. 코드 통합 승인, 코호트 시작 승인, 과학적 성공 판정은 별개다. 아래 G는 다음 단계 진입에 필요한 관문(gate)이다.

역할 배치 예로, 사람 소유자가 연구 질문·위험 수용·최종 주장을 맡고 Claude 조정자가 표본 분리·예산·실행 예약·봉인 근거를 모은다. Codex 또는 Sonnet 한 명이 구현하며, **그 구현에 참여하지 않은 별도 검토자**가 제어/평가 경계와 통계 계획을 확인한다. 스크립트가 생성·대조할 수 있는 일에는 검토 모델을 호출하지 않는다. 모델 이름보다 작성자와 검토자의 역할 분리, 실제 반례와 검사 근거가 중요하다.

```text
G0  조정자/소유자: 질문·위험 등급·예산·분리 자료·작업 소유자 확정
    공통 연구 계약은 기존 검토본 재사용; 달라진 과학적 의미는 먼저 검토
     |
     v
    탐색 루프: 구현자 1명, 같은 PR / 같은 opt-in 구현 / dev 자료만
    변경마다 commit + 구성 hash + 실패 기록; 필요한 검사·유한 probe
    이 루프의 성능은 exploratory; confirmatory 자료에는 접근하지 않음
     |
G1  후보 C 선택·commit 고정: 후보 구성 + split + 분석/판정 + N/중단 규칙
    자동 생성: 의존성 closure·manifest·등록 diff·known-case 인수 목록
     |
     +-------------------------+-------------------------+
     |                         |                         |
    A: 결정적 자동 검사       B: 독립 검토자 1명       C: 인수 확인
    CI·schema·hash·OFF 경로    diff+계약+반례 검토      동일 후보의 알려진 dev 사례
    조정자가 receipt 수집     작성자와 분리           runner/가드 이관이면 필수
     |                         |                         |
     +-------------------------+-------------------------+
     |  검토/실행은 같은 C를 본다. CPU 검사와 물리는 공용 Mac에서 경쟁시키지 않음.
     |  C의 인수는 dev 자료로만. 실행 권한/잠금 필요. 준비되지 않았으면 A/B부터.
     |  수정 발생 -> 새 C, 영향 검사/인수 재실행 + 독립 검토자가 변경분 재확인
     v
G2  조정자: A/B/C 근거 일치 + blocking 해결 + 최종 commit/config 일치
    소유자 규칙에 맞는 통합 승인 후 정확한 실행 snapshot·등록 receipt 봉인
    통합 시 runtime/분석 입력이 바뀌면 G1로; 같으면 차이 증명과 provenance 추가
     |
G3  확증 시작: 사전 선언한 새 자료·비교 조건·고정 소스, 잠금/예산 확보
    조정자/runner가 사전 중단·HOST_ERROR 규칙 집행; 중간 튜닝 금지
    대기 중 다른 에이전트는 빈 결과표·보고 도구 준비만 가능
     |
G4  결과 공개: 성공/실패/중단·모든 분모·구간·비용·일탈·원본 hash
    자동 등록부 -> README/PR + native TensorBoard export/readback
    소유자: 주장의 범위·채택 결정; 실패 후보도 그대로 보존
```

물리 인수 C는 무조건 생략하는 단계가 아니다. 실행기 이관·물리·타이밍·가드 경계 변경에는 필수다. 동일한 코드·구성으로 이미 수행한 **해당 후보의 적합한 dev 인수 기록**이 있으면 다시 포장했다는 이유만으로 똑같이 실행할 필요가 있는지 판단할 수 있다. 이 재사용은 확증 표본에 dev 성능을 더하는 일이 아니며, 정확한 해시·실제 적용값·환경·검토 범위가 같아야 한다. #292처럼 탐색/등록 코드가 다른 현재 후보는 여기에 해당한다고 가정하지 않는다.

독립 검토자가 코호트의 숨겨진 결과를 열어 구현자에게 전달하면 분리가 깨진다. A/B/C는 알려진 dev 자료로만 수행한다. G2 이후 코호트 결과에 영향을 주는 변경은 새 후보이며, 종료 뒤 최종 보고에서 이를 밝힌다. 해시만 같다고 실행 환경이나 모델 제공자 상태까지 같다고 보지도 않는다.

### 6.1 작은 제어기 수정의 시간 예산

아래 수치는 **사전 계획용 시나리오**다. 현재 작업을 계측한 결과도, 문헌이 보장한 수치도 아니다. 다음 조건을 둔다: 수십 줄 변경, 이미 성숙한 공통 계약·도구, 리뷰어 즉시 배정, 연구 질문/심판/물리 불변, 추가 결함 수정 없음. 코드 수정은 G1 전에 끝난다. 이후 A/B/C는 같은 후보를 검증한다.

| 구간 | 비교용 직렬 절차 가정 | v2 가정 | 계산 근거 |
|---|---:|---:|---|
| 문제 확인·구현·관련 검사 준비 | 30분 | 30분 | 동일한 구현 난이도 |
| 개별 요청·인계·검토 대기 | 90분 | 10분 | 대기 감소 목표이며 가장 큰 미측정 항목 |
| 자동 검사 10 + 독립 검토 20 + 인수 20 | 50분 | 20분 | 직렬 합 50 → 독립 실행의 최댓값 20; 별도 CI 자원 전제 |
| 등록 문서·번호·봉인 | 35분 | 10분 | 공통 계약·자동 생성기를 이미 갖춘 경우 |
| 결과 대조·문서/TensorBoard 표시 | 15분 | 10분 | export/readback을 포함한 목표; raw 크면 더 걸림 |
| **코호트 자체를 제외한 합계** | **220분** | **80분** | 차이 140분, 관리·검증 경과시간 63.6% 감소라는 가정 |

따라서 확증 첫 실행까지 약 **70분**, 결과 공개까지 **80분 + T_cohort**가 목표다. 안정된 도구가 없는 초기 이행에서는 **80–120분 + T_cohort + 자원 대기 + 재작업**으로 잡는 편이 낫다. 20분을 넘었다는 이유로 독립 검토를 끝내거나 인수를 통과 처리하지 않는다.

`T_cohort = Σ(실행별 wall 시간 + 초기화/저장 시간) / 검증된 병렬 처리 효과`로 따로 견적한다. 예를 들어 **60회 × 회당 1.5분 = 90분**, 단일 슬롯·별도 추가 비용 없음이라는 가정이면 전체는 **310→170분**, 약 **45.2% 단축**이다. 현재 #292의 72 cases는 60개의 독립·동일 비용 실행과 같지 않다. 실제 계획의 조건 수·seed·반복·초기화·자원 잠금 대기를 넣어 다시 계산해야 한다. SIM 초를 wall 분으로 바꾸는 근거가 없으면 예상 완료 시각을 확정할 수 없다.

공용 Mac에서 A와 C를 동시에 돌릴 수 없어 10분 검사가 인수 앞에 붙으면 v2는 90분+T가 된다. 한 번의 수정으로 검토·인수 20분이 다시 필요하면 그만큼 늘어난다. 코호트가 6시간이면 위 140분 절감도 전체의 24.1%이고, 코호트가 30분이면 56.0%다. 이 민감도가 먼저 줄일 병목을 정한다.

### 6.2 도입 순서와 확인 방법

1. **기록부터**: 다음 5개 작은 변경에서 단계 시작/종료·queue wait·재작업 이유를 기존 실험 기록에 추가한다. 첫 변경 시각부터 최종 결론까지 잰다. 5개는 통계적 효과 확정용 N이 아니라 병목 발견용 유한 관찰이다.
2. **행정 비용부터**: 같은 후보에 검토 입력 묶음 1개, 검토자 1명, 공통 계약 재사용, 알려진 인수와 검토 병렬화를 적용한다. 이것만으로도 줄지 않으면 새 도구 도입보다 대기 원인을 본다.
3. **작은 도구 PR**: manifest/등록 표 생성, R0 문서 전용 검사, 후보 상태 등록부 순서. 변경된 runtime·config·평가 입력을 놓치지 않는 음성/양성 대조를 함께 검토한다. frozen 기록은 변환·덮어쓰지 않는다.
4. **후속 설계 PR**: 번호/해시 분리와 같은 구현의 dev→확증 승격. 구형 reader와 새 reader를 병행 검증한 뒤 전환한다. 정상 기준선과 오류 주입에서 판정이 같고, 모든 legacy 기록이 원래 SHA에서 해석되는지 확인한다.
5. **통계 설계는 마지막**: 공학적 불합격 확정 종료를 먼저 검토하고, 그래도 코호트 비용이 지배적일 때 순차 검정·적응 설계를 설계한다. 그 설계의 오류율/검정력을 검증하기 전에는 확증에 사용하지 않는다.

비교 지표는 전체 경과시간의 중앙값·상위 지연, 재검토 횟수·대기, 원인별 재작업, 봉인 후 source mismatch, 누락한 검사, 무효 코호트, 실패 결과의 보존 여부다. 작은 전후 비교는 난이도·모델·동시 부하가 다르면 인과 효과가 아니므로 조건을 같이 적는다. “실패 가설을 빨리 폐기했다”도 연구 진척이며 성공률을 높이려고 실패를 제외하지 않는다. 새 상시 모니터링·예약 작업은 제안 범위에 포함하지 않는다.

## 8. 검증·남은 일

이 변경은 문서 1개뿐이다. 문헌의 주장을 UGRP 실측과 구분했고, 현재 #292의 인수 조건·소스 고정을 면제하지 않았다. 의존성 자동 추적과 CI 분할이 이미 있다는 점도 반영했다. 정적 문서 검증 결과는 아래에 기록한다.

- 범위: 내부 링크 대상, 출처 ID의 참조/정의 일치, 코드 블록/표 구조, 시간 예산 산술, 공백 오류.
- 정적 확인: 출처 39개 정의·참조 일치, 내부 파일 링크 8개 존재, 표 118행의 열 수 일치, 코드 블록 닫힘, 220→80분·310→170분 및 민감도 산술을 Python 표준 라이브러리로 확인했다. 이것은 문서 검사이며 연구 성능 테스트가 아니다.
- 실행하지 않은 것: pytest 전체 suite, 물리·시뮬레이션·렌더링·학습/추론·추가 모델, 새 코호트, TensorBoard 변환/서버, Drive 작업.
- 2026-09-30 정정: 기존 문구는 “실행 없음”을 GitHub CI까지 금지하는 것으로 잘못 해석하여 CI 생략을 지시했다. 정상 GitHub CI는 허용되며 필수 검증이다. 후속 커밋은 CI 생략 표시를 사용하지 않고 실행 중인 CI도 취소하지 않는다. 위 로컬 미실행 기록은 그대로이며, 과거 CI의 통과를 소급 주장하지 않는다.
- 다음 단계: 조정자가 위험 등급·공통 계약·검토 역할을 검토한 뒤 작은 도구/정책 PR로 나눌 수 있다. 기존 독립 검토와 소유자 규칙의 대체는 이 조사 PR 자체가 수행하지 않는다.
