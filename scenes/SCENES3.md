## 공통 규칙 (모든 장면)

## 한계와 확인 안 됨
- **초(s) 값은 장면 선별용이지 예측이 아니다.** 이 모형은 문을 8 s 만 직렬로 보고 3대 오라클 완료를 192~221 s 로 잡지만, 실제 3대 실행은 이보다 오래 걸린다(앞 로봇이 `carry_finished` 할 때까지 뒤 로봇이 문 앞에서 기다림, `scripts/run_team_carry.py` 의 문 대기열, 개발 실행에서 관찰). 특히 X3 의 "T0 끝 − 오라클 완료 ≥ 60 s" 기준은 직렬 문이 흡수하거나 순서를 바꿀 수 있다. 개수·표식 기준(L3·C3·K3·D3 의 오배송)은 이 영향이 작다.
- **X3·D3 는 "T0 가 추측해야 하는 부분"이 개수 차이로는 없다.** X3 는 T0 에서 아무도 추측하지 않고 개수 차이 0(시간만 차이), D3 는 맹인이 추측(미끼 이동)하지만 개수 차이 0(오배송만 차이)이다. 기존 2대 정의를 그대로 3대로 옮긴 결과이며, 개수 차이를 원하면 6슬롯을 L3·C3 로 바꿔 다시 만들면 된다(설계 결정).
- 3대 장면의 기하는 2대 본 실험 장면보다 엄격하다(문 1.5 m·상자 벽 0.55 m 등, 위 근거). 같은 조건의 비교가 아니다.
- `type_code` L3·K3 는 `analyze_main.scene_type` 이 옛 K301–L303 에서 만들어 내는 값과 같다. 옛 7개와 이 30개를 유형 단위로 합산하지 말 것.
- 시뮬레이션·VM·LLM 실행 없음. 집기 시간이 거리에 비례한다는 가정, 문 점유 8 s, 시야·RGB 검출(0.8 m 초과), 로봇 크기 0.25 m(시선 가림)는 DESIGN-COOP 가정 그대로이며 측정 안 됨. 3대 FixedPlan(기준선)의 물리 성공도 확인 안 됨(관문 결과는 이 작업 밖).
- T1 대 T2 차이는 확인 안 됨. 장면은 중심 로봇을 r1/r2/r3 에 균형 있게 두었을 뿐이다. C3 는 정보 부족이 아니라 조정 문제라 오라클 계획에서 모든 로봇이 자기가 아는 주문을 나를 수도 있어 `info_flow`가 비는 장면이 있다(참고용 파생값).
- C3 의 S 차이는 정확히 0.50(경계, 오차 1e-6 허용, v2 의 C 와 같은 상황). 파트너 B 가 A 의 가장 낮은 ID 주문을 알도록 정해서 U 에서도 차이가 생기게 했으므로 "B 는 항상 낮은 ID 주문을 안다"는 편향이 C3 전체에 있다.
- 기준선 U·S 는 해석 모형이다. 실제 T0 LLM 은 다르게 고를 수 있다(특히 "가장 낮은 ID 주문을 고른다"). D3·X3 의 T0 는 모형에서 개수가 같지만 실제 LLM 이 헤맬 수 있다.
- 좌표는 고정 seed 무작위 표집(0.05 m 격자)이고 손 설계가 아니다. 좌표·상자 ID·정답은 평가 전용이며 LLM 입력 금지. 프롬프트가 주문을 어떤 순서·ID 로 보여주는지는 ID 순서로 가정했다.
- 표본 거절(장면 탈락 아님, 좌표 재추출): L3 14,697, C3 19,287, K3 5,029, X3 98,787, D3 18,871번 뽑아 각 9/9/6/3/3 장면을 얻음(사유별 횟수는 JSON `rejections_by_type`).
