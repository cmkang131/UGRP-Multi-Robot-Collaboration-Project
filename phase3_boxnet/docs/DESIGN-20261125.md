## D1. Question
In a team where every robot runs its own small LLM, the team's plan can be divided so that one call plans for all
robots, for a sub-team, or for one robot. When the output limit is lowered, or when what a call must read grows,
which failure blocks the team's next action under each division, and how many tokens does one delivered order cost?
- Output limit (max output tokens): bounds what one call can WRITE; hidden reasoning and the visible answer share it.
- Context rot: judgement gets worse when what a call must READ grows, although the current state and everything
  needed is still in the prompt.

## D3. Changes to the task
1. PLAN UNIT (exactly one, identical in both fidelities): a writer writes, for each robot it is responsible for, that
   robot's whole QUEUE of carries until the open orders are served. Queue entries: `{"box": colour, "zone": zone}`,
   `{"wait_for": order_id}` (do not pass the door before that order has been set down), final `"finish"`.
   Reason: today a meeting gives each robot ONE next action, the reply is about 380 generated tokens for 3 robots
   (archived calls at limit 2048: central plan median 376.5, max 662), so an output limit could never bind. This
   replaces "plan five steps at once", which was a BoxNet condition.
   The planner keeps the queues and hands the executor the next entry at each decision point without calling an LLM.
   A new meeting opens only when the stored plan cannot continue (an entry is impossible, a queue is exhausted while
   orders are open, a `wait_for` can never be satisfied) - to be specified.
2. WORKLOAD (one value): 2 orders per robot (6 / 12 / 18 orders), plus one box without an order per 3 robots
   (a decoy, so that "delivering an order twice" and "using a box that is not needed" can show).
3. DEPENDENCE BETWEEN SUB-TEAMS: one box room and one pool of orders shared by all robots; precedence rules
   ("order A must be set down before order B") that, at 6 and 9 robots, link orders that a sub-team-local plan would
   give to different sub-teams. Only scenes pass in which a scripted "each sub-team plans alone" solver loses points
   (rule violation, duplicate, or clearly longer completion) relative to the team-wide oracle.
4. DOORS: not fixed yet. Neon's review 3 says one door per three robots; the user's guide says fewer doors than
   sub-teams. To be decided by the scripted check of item 3 and by how long the 3-robot MuJoCo run takes.

## D3.1 (new). One plan unit: the next five steps of every robot the writer is responsible for
- A STEP is one decision the executor already asks the planner for. The planner's `decide` has four such points
  (`20261123-phase3/link/brain/frameworks.py`, `decide` / `action`, about lines 398 to 482): `pick`, `destination`,
  `door`, `next`. Step vocabulary, one kind per point:
  - at pick: `{"pick": colour}`
  - at destination: `{"zone": zone}`
  - at door: `"pass"` or `{"wait_for": order_id}` (stay before the door until that order has been set down, then pass)
  - at next: `"back"` (return for another box) or `"finish"`
  One carry = four steps. Five steps = one carry and the pick of the next one.
- LEGALITY: a robot's list must follow the cycle pick, destination, door, next, starting at the point the robot is at
  now; it may be shorter than five only if it ends with `"finish"`. A list that breaks this is an unusable reply
  (form), repaired with the same number of chances for every writer.
- CONSUMPTION: no clock ticks. A step is consumed when the robot reaches that decision point and the planner hands
  it out. `wait_for` answers "wait" at the door until the named order is set down and is consumed when the robot
  passes. This must mean the same in the text simulation and in MuJoCo.
- MEETINGS: the first meeting opens when all robots have reported their first scan (as today). Later meetings open
  when a robot reaches a decision point with no stored step, or when its stored step is impossible in the current
  state. Default rule R1: at every meeting every writer rewrites five steps for all of its robots from their current
  points (unused steps are discarded). Alternative R2: only robots without a usable step get new steps.
  UNDECIDED between R1 and R2; reviewers are asked to count meetings and written steps per episode for both from
  the oracle trip timestamps in the scenes (no model needed).
- HISTORY: every prompt carries the executed steps so far (robot, step, outcome such as "set down, order o3
  delivered" or "waited"), followed by the current board. E2 (reading) now varies this history on a saved state:
  none / last meeting only / all; the current board always stays and is placed after the history.
- Structures: leader writes N x 5 steps in one reply (45 at 9 robots), a sub-team leader 15, an own writer 5.
- E1, C, measures, workload, dependence between sub-teams, doors, gates: as in draft 1.
- New in measures: a cut-off with an empty visible answer (reasoning filled the limit) is counted separately from a
  cut-off in the middle of the answer.
- NOT VERIFIED: that the MuJoCo executor can run stored steps with no change on its side. `action()` has paths for
  `locked`, `releasing` and put-down on a colour mismatch that a step list has to respect.
