# TASK-CHEN2D-11: plan several steps per call, for a leader and for robots that write only their own actions (2026-11-24)

Context: tasks 1 to 10 are done (`REPORT-CHEN2D.md`; 118 tests pass). Same hard limits: this folder only, no network, fake model for tests, no real-model batches, nothing under `20261123-phase3/` may be edited. Every existing option keeps its behaviour byte for byte; all existing tests stay green.

Why. The user's idea (their words): "출력한도가 높을 수 밖에 없는 일을 시키는 건어때?" and, about planning several steps at once, "이건 팀장만 하는 건가 아니면 팀원도 하는 건가?" then "ㅇㅇ 한번 그렇게 설계해서 확인해봐". Today the leader's reply is 150 to 300 tokens whatever the team size, so the output limit only bites when it is cut artificially (1,024). A robot-borne LLM is slow, so planning several steps per call is natural; then the leader must write for every robot and every step in one reply, while a robot that plans only for itself writes one action per step. A hand probe (authors' leader prompt, last sentence changed to "plan the next H steps", GLM) gave replies of about 1,500 to 3,600 tokens for H = 5 or 10 at 4 to 32 robots against 160 to 1,400 for H = 1; the model sometimes wrapped the list as `{"plans": [...]}`.

## H1. `--horizon H` (default 1 = today's behaviour byte for byte)
For CMAS with H > 1:
- Prompt: the authors' leader prompt (history options of task 9 still apply) with its last instruction "Include an agent only if it has a task next. Now, plan the next step:" replaced by: "Include an agent only if it has a task in that step. Plan the next {H} steps at once: output a JSON list of {H} such plans, one per step, in order, assuming every earlier step of your plan has been executed. Use an empty object for a step with nothing to do, and stop the list early if the task is complete. Now, plan the next {H} steps:".
- Parsing (lenient mode): accept a JSON list of objects, or one object whose single value is such a list (e.g. `{"plans": [...]}`), found after the last "EXECUTE" if present; a single object counts as a list of one. Strict mode: only a bare list.
- Execution of one planning round: take the plans in order; check each plan against the state AT THAT MOMENT with the authors' checker (the single-proposal check of task 9); a valid plan is applied as one environment step with the authors' executor; at the first plan that is empty-because-complete, stop (task state decides success as today); at the first plan with any action that is not doable, discard it and all later plans and end the round. The authors' repair loop (feedback and re-prompt, up to their limit) applies only when the FIRST plan of the round is invalid or the reply cannot be parsed; the re-prompt asks for the whole list again.
- The authors' iteration limit counts planning rounds as today. Record per round: plans proposed, plans executed, stop reason (all executed / invalid at position t / complete / parse failure / output limit). Record environment steps separately from planning rounds everywhere (`steps` keeps its meaning of environment steps; add `planning_rounds`).

## H2. Framework `OWN` (ours, not the authors'; describe it as "no leader, every robot writes only its own actions, the program merges them")
- One planning round = one call to each robot that has at least one doable action in the current state, in the authors' agent order. No leader, no final joint plan written by a model.
- Prompt: the authors' DMAS dialogue prompt (same state of self and of all others, same history options) with the blocks from "[Action Output Instruction]" to "Your response:" replaced by an instruction to output ONLY the robot's own actions for the next H steps: a JSON list of H entries, each either one action string for itself (same action syntax) or null, assuming its own earlier entries were executed; it sees, as the dialogue block, the lists already proposed by the robots that spoke before it in this round and is told to avoid conflicts with them and not to write actions for others. For H = 1 the list has one entry.
- The program merges: the joint plan of step t is {agent: its t-th entry} over the non-null entries. Execution and stopping rules are exactly those of H1 (same checker, same "first invalid joint plan ends the round"). Repair, first plan only: each robot whose own first entry is not doable gets the authors' feedback sentence for its own task and is asked for its whole list again, up to the same number of iterations as the authors' loop in total; other robots are not re-asked.
- All meters (calls, tokens, cut-offs, limits, call ceilings, history options, `--max-output-tokens`, retries) work as for the other frameworks; `OWN` with `--horizon 1` is allowed.
- Tools: `summarize.py`, `failure_causes.py`, `output_demand.py`, `cost.py` must accept `OWN` and group by horizon; paired tools may refuse to mix horizons.
