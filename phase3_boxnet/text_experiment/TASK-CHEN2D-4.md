# TASK-CHEN2D-4: the drop-off must not give the news away (2026-11-24)

Context: tasks 1 to 3 are done (`REPORT-CHEN2D.md`). Same hard limits (this folder only, no network, fake model for tests, no real-model batches).

Finding in the first real batch (`../20261124-chen2d-snap-v3/runs/glm-batch1-v3`): with `--tell member` the central planner is never told, yet in `4x8_CMAS_e1_member_env0` it carried box_green seven squares to `dropoff_green` although target_green was closer, and in `2x2_CMAS_e1_member_env1` it put one box_orange into `dropoff_orange` and another into `target_orange`. The item `dropoff_A` that appears in the shared state at the event names the colour, so an LLM that was not told can guess the change. The manipulation "who is told" needs a world in which the state alone does not reveal the new order.

## F1. A neutral drop-off that is always there (`--dropoff always | event`, default `always`; `event` = today's behaviour, kept for comparison and for the existing tests)
- With `always`: every map has ONE item named exactly `dropoff` in square D from the initial state on, in every condition including `static`. D is the square already enrolled for e1 (for `static` and e1) and D2 for e2. No colour in its name.
- From the initial state on, for every box (any colour) that is in the square of the drop-off, the doable-action list of that square's agent contains `move(box_X, dropoff)`, listed after the authors' actions. It is always physically possible: the box is removed, the drop-off stays.
- What counts: putting a box into the drop-off is a WRONG delivery, except a box of colour A after the e1 event (then it is the correct delivery) and the returned box after the e2 trigger. Putting a box of colour A into target_A after the e1 event stays a wrong delivery, as today. All wrong deliveries are irreversible.
- The authors' task sentence in the prompts is not changed. Nothing in any prompt explains the drop-off, except the change-of-orders block, whose wording becomes: `Change of orders (announced after step K): the order for boxes of colour A has changed. They are no longer wanted in target_A. They are now wanted in the dropoff at square[D]. A box_A that is put into target_A from now on counts as a wrong delivery.` Under `--tell leader | member` only the told prompts carry it (unchanged rule).
- `static` with `--dropoff always` is therefore no longer byte-identical to the authors' prompts (one extra item and sometimes one extra doable action). Keep a pure-upstream static available as `--dropoff event` and keep the upstream parity tests on it. Report this as a deviation.
- e2 under `always`: the cancelled box comes back under its ORDINARY name (`box_A2`), not `..._returned`; the environment tracks which box it is by an internal id (if another box_A2 is in the same square, the returned one is the one whose delivery was cancelled; when a box_A2 leaves that square, the agent's action moves the returned one first only if the plan says so; simplest correct rule: keep an internal list of box ids per square and let `move(box_A2, ...)` take the returned one LAST unless it is the only one; state the rule you implement and test it). Its correct destination is the drop-off; any target_A2 is wrong for it. The told robots get: `Change of orders (announced after step K): the box of colour A2 that was just delivered at square[X] was not accepted. It is back in square[X] and is now wanted in the dropoff at square[D2].`
- Completion and strict success unchanged in meaning: no box left and no wrong delivery. Note that with `always` a team that was never told can still finish with the authors' `success` label by putting box_A into target_A (wrong) or leaving... (it cannot leave it: completion counts boxes); record as today.
