## 3. 지시 튜플 계약 (녹화 = 배포)

공개 튜플은 `(skill, object_kind, role, destination_zone)`이고 `harness.solo_carry_contract.instruction()` 하나가 만든다.
recorder와 학생 둘 다 이 함수를 호출한다.

| 구간 | 튜플 |
|---|---|
| 파지(READY/GO 대기 중) | `('wait', 'cyan', 'west', 'none')` |
| 파지 | `('grasp', 'cyan', 'west', 'none')` |
| 운반·놓기 | `('release', 'cyan', 'west', 'B')` |

- **역할:** v5 어휘에서 상자의 유일한 역할은 `'west'`다(`KIND_ROLES`, 같은 모양 보정 블록의 파지 이름도 `'west'`: `sim/zone_cargo.py:211`). 이전 판의 `'solo'` 특수 처리(역할을 바꿔 검사하는 shim)는 없앴다.
  `validate_solo_observation`은 수정하지 않은 v5 `validate_observation`을 그대로 부르고, 이 작업의 종류(cyan)·역할(west)만 추가로 요구한다.
  시험 `test_every_recorded_and_deployed_row_is_a_plain_v5_observation_the_loader_can_encode`가 recorder 행과 학생 행 전부(wait·grasp·release)를 v5 `validate_observation`과
  loader가 쓰는 `context()`(`harness/grasp_act.py:56`)에 통과시키고 one-hot이 cyan·west인지 확인한다. loader 자체(`harness/grasp_act.py`)는 torch/lerobot이 필요해 이 환경에서 import하지 않았다(미확인).
- `'west'`는 토큰일 뿐 세계 서쪽을 뜻하지 않는다. 교사는 상자의 보이는 yaw를 처음 볼 때 로봇 쪽으로 180° 접어(fold) 그 면에서 접근한다(상자가 180° 대칭이라 두 면이 같은 파지). 접는 방향은 고정(latch)한다
  (작업자 설계, 사용자 미확인 — §7-9).
- 교사 내부 끝 토큰(`teal`), 교사의 handoff 플래그, 러너가 계산한 시계는 녹화 행에 남지 않는다. `skill_elapsed_s`는 공개 튜플이 바뀔 때만 초기화하고,
  `pwm_elapsed_s`는 v7 deadband-2 own clock(`DeadbandIssuedClock`) 값을 그대로 기록한다(두 구간에 걸쳐 시계 객체 하나).
- 시험 `test_recorded_rows_equal_deployed_rows_field_for_field_including_own_clocks`가 wait→grasp→release 열 전체(튜플, 두 시계, rgb 참조, 발행 이력, sample_id)를 recorder 행과 학생 행에서 같게 확인한다.

## 4. 평가 게이트 (평가 전용, 교사·학생 입력 아님)

`harness/solo_carry_eval.py::evaluate(rows, slot, rid, *, lower_start_t, cap_s, t0=None)` — `eval-only.jsonl` 행(`beam` 키가 상자를 담음)을 읽는다.
관측되지 않은 값(없음/None/비유한/음수 접촉, 높이)은 그 값을 쓰는 게이트를 **실패**시킨다. 순서대로 첫 실패가 `failure`다.

| 게이트 | 정의 | 상수의 출처 |
|---|---|---|
| `lift` | min_z ≥ 0.012 m, tilt ≤ 10°, 양 손가락 각 ≥ 0.5 N이 3 s 연속. 접촉 미관측 행이 하나라도 있으면 실패 | `LiftScore.CRITERIA`(dsh/pairact-r1-dryrun) = 트리 내 `HOLD_MIN_Z_M`/`HOLD_MIN_FORCE` |
| `no_drop` | 안정 들기 시작부터 명령된 내려놓기 시작(`lower_start_t`) 전까지 min_z가 0.012 m 아래로 내려간 행이 없음(dwell 0, 엄격) | 사양 문구 |
| `slot` | 마지막 행의 상자 발자국(34 × 40 mm, 상자 자신의 yaw 포함)의 네 꼭짓점이 plan의 zone B 슬롯 직사각형(슬롯 yaw 포함) 안. yaw 미관측이면 실패 | `sim/zone_arena.py:46` `BOX_HALF` |
| `rest` | 마지막 1 s: min_z ≤ 6 mm, tilt ≤ 5°, 이동 ≤ 5 mm, 손가락 하중 < 0.1 N | `pair_carry_eval.Criteria`(트리 내) |
| `release` | `lower_start_t` 이후 양 손가락이 처음 < 0.1 N인 행에서 바닥 높이 [−5, 6] mm, 이후 상자 속도 ≤ 0.02 m/s, tilt ≤ 10° | `SoloScore.RELEASE_CRITERIA`(dsh/pairact-r1-dryrun) |
| `completion` | release 시각 + 1 s(rest 창)가 `t0` + `cap_s` 이내 | `cap_s`는 **필수 인자, 기본값 없음** |

러너는 `cap_s + carry_cap_s`(기본 60 + 110)를 `cap_s`로, 에피소드 시작을 `t0`로 넘긴다. 결과는 `carry-eval.json`, `result.json`의 `solo_carry_eval`,
`carry_success`에 기록되고 `record_training`일 때 `physical_success = grasp_physical_success AND carry_success`다(pair 흐름과 같은 방식).

## 6. 아직 검증되지 않은 것

- 물리 시뮬레이션을 한 번도 돌리지 않았다. GPU 없음, 기준선(baseline) 없음, 교사 성공률·학생 성공률 없음.
- 장면 연결: `select_solo_cargo`는 실제 `ScenarioFinalV3Scene`(s6·s1 v6) 설정으로 CPU 시험했다. 그러나 `place_solo_cargo`(free joint qpos에 plan pose 쓰기)는 `mujoco`가 이 환경에 없어
  시험이 skip된다(`test_place_solo_cargo_sets_the_plan_pose_on_the_free_joint`). `snapshot()`이 `SoloBox`로 동작하는지, `finger_forces`가 `cargo_cyan_1_geom` 접촉에서 값을 내는지,
  러너의 start/finalize 훅은 실행된 적이 없다. setup 뒤 0이 아닌 yaw로 옮긴 상자가 이후 리셋 없이 유지되는지도 미확인이다(시나리오 로더는 상자 setup yaw를 0으로 강제한다: `sim/zone_scenario_scene.py:43-46`).
- `VisibleOnlyGraspTeacher`가 상자를 실제로 접근·정렬·파지하는지. 어댑터는 (a) 보이는 상자 yaw를 로봇 쪽으로 접어 고정하고 (b) `visible_probes`를 `max(5, visible_n)`로 바꾸며
  (c) 파지 높이를 상자 보정값 0.024 m로 둔다. 상자 파지 기하는 생산 상자 보정과 같지만 이 교사로 상자를 잡은 물리 결과는 없다.
- 상자 색의 렌더 hue: 명목 RGBA만 확인했다. 다른 교사의 GCP 진단에서 cyan 마스크 교집합 0 px(`unknown`)가 나왔고 원인은 미결정이다. 학생이 자기 RGB로 상자를 구별하는지는 미측정이다.
- 쌍 빔(`beam_1`)과 다른 상자는 장면에 남아 정지 방해물이다. 파지 교사는 `beam_1`을 장애물에서 제외하므로 plan이 빔을 상자·로봇 출발·경로에서 멀리 두어야 한다. 운반 교사는 빔과 다른 상자를 원판 장애물로 본다.
  plan 생성기는 없다(§7).
- 운반 경로는 쌍의 `carry_route`(빔 기하 기반 보수적 envelope 포함)를 그대로 쓴다. 직선 경로만 있고 우회 탐색(`detour_v1`)은 없다 — 막히면 `route_blocked`로 명시적으로 실패한다.
- 쌍 교사의 `_route`(VisibleOnlyGraspTeacher)는 쓰지 않았다: 그것은 보이는 월드의 오도메트리 좌표계에서 보이는 벽으로 계획하는데 슬롯은 월드 좌표 plan pose라 둘을 잇는 앵커가 검증되지 않았다.
  운반 교사는 쌍과 같은 정답 교사 예외(시연 전용)다.
- 학생: chunk executor와 READY barrier는 `harness/pairact_r1.py`(dsh/pairact-r1-dryrun)에 있고 이 트리에 없다. 주입하거나 지연 import 한다. 체크포인트로 돌린 적 없고, 러너에서 solo 학생 평가는 연결하지 않았다(`student_eval`과 함께 쓰면 거부).
- 라벨 파일의 `local_distance_m`(특권 정답)은 빔 기하로 계산되어 solo에서는 의미가 없다(교사 파일 전용, 학생 입력 아님).
- 이전 판의 can 결과는 없다(물리 실행 0회). 상자 판은 새 버전이며 어떤 결과와도 합산하지 않는다.

## 7. 실행 전에 동결해야 할 숫자·결정 (open pins)

1. **release 속도 임계값**: 0.02 m/s는 `SoloScore.RELEASE_CRITERIA`(`dsh/pairact-r1-dryrun:harness/grasp_act_rollout.py`, 커밋 `c3747f4b5` 기준)에서 복사했다. 그 파일은 pinned 트리에 없으므로 이 값을 이 실험의 사전 등록에 직접 고정해야 한다.
   같은 이유로 finger_max 0.1 N, 바닥 높이 [−5, 6] mm, tilt 10°도 함께 고정할 것. 위치: `harness/solo_carry_eval.py::Criteria`.
2. **completion cap**: `cap_s`는 의도적으로 기본값이 없다. 러너는 `cap_s + carry_cap_s`를 넘기고 carry cap은 ≤ 120 s로 검증한다. 이상적 추종 rollout이 handover 후 약 75 s를 쓰므로(`v_max=0.08 m/s`) 실제 추종 지연 여유를 정해야 한다.
3. 교사 `Params`(속도·허용오차·phase cap)는 쌍 P2의 후보 상수 그대로다. 이 실험용 측정값이 아니다.
4. `no_drop` dwell(현재 0 = 한 행이라도), rest 창(1 s), 슬롯 직사각형 크기와 pose, 슬롯 기준 로봇 서 있는 자리의 벽 여유(`ROBOT_RADIUS_M=0.17`). `slot_margin_m`=0(상자 발자국이 슬롯 안이기만 하면 됨).
5. ~~role 어휘~~ — 해결: v5 상자 역할 `'west'`(§3).
6. plan 필드(`solo_cargo`={`cyan_1`, `cyan`, pose}, `solo_slot`, `roles={'r1':'teal'}`, `cargo_scene='cargo_v6'`)를 만드는 생성기와 그 해시 규칙(없음), 시나리오 선택(후보 `s6_novel_relation_v6`, cyan 유일 장면만 허용).
   시험의 슬롯 값(4.6, −2.1, 반폭 0.10)과 상자 pose(0.7, −1.5)는 예시이지 설계값이 아니다. 상자 초기 yaw 분포도 정하지 않았다.
7. `record_training` 경로의 승인 증명(teacher gate, 640×480 기록 점검)은 기존 pair 경로의 것을 그대로 요구한다. solo용 교사 관문(≥ 38/40 등)은 정의하지 않았다.
8. `plan['end_color_scene']`: teal/blue 끝 색 장면(`grasp_act_teal_blue_v1`)을 켤지. 켜면 남아 있는 빔의 teal 띠(hue 78.7)가 cyan 범위(84–100)와 5.3 차이다. 렌더 hue 측정 전에는 정하지 않는다.
9. 상자 접근 면 규칙(처음 본 yaw를 로봇 쪽으로 180° 접어 고정)은 이 작업자의 설계이며 사용자 확인 전이다. 근거는 상자 발자국의 180° 대칭(`sim/zone_cargo.py:208-213`)뿐이고 물리로 확인하지 않았다.
