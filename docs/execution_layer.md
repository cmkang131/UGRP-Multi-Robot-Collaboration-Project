# 실행층

계획층이 고른 행동을 바퀴와 관절 명령으로 바꾸고, 결과를 계획층에 보고한다. 로봇마다 하나씩 돈다. 이 문서는 [전체 구조](architecture.md)의 실행층 세부다. 2026-11-16 동결 직전 설계 기준이다. 로봇 한 대의 단계별 설명(둘러보기, 정면 맞추기, ACT 모델)은 [Solo 구조와 모델](solo_architecture.md)에 있고, 무엇을 고르는지는 [계획기와 메시지 규칙](planning_messages.md)에 있다.

## 1. 고른 행동과 실행

| 고른 행동 | 실행 | 누가 |
|---|---|---|
| 집을 상자 | 다가가기, 정면 맞추기 → 집기·들기 → 들었는지 확인. 빈손이면 계획기에 알리고 다시 둘러본 뒤 다시 고른다 | 코드 → ACT → 코드 |
| 목적지 | 문으로 가서 지나가기 → 표식을 찾아 그 앞으로 → 내려놓기 | 코드 |
| 문 | 지금이면 지나간다. 기다리면 상자를 든 채 집은 자리에서 선다 | 코드 |
| 내려놓고 끝내기 | 팔을 내리고 놓은 뒤 그 로봇의 실행이 끝난다 | 코드 |
| 메시지 덧붙이기 | 팀 구조가 정한 상대에게 전달 | 통신 |

## 2. 왜 이렇게 나눴나

- 계획은 LLM: 누가 무엇을 맡을지, 알릴지 말지는 상황마다 달라 규칙으로 적기 어렵다.
- 집기는 ACT: 집게와 상자가 닿는 구간은 화면을 보고 고쳐 가는 쪽이 낫다.
- 이동은 코드: 학습 모델로 이동까지 시켰을 때 처음 보는 장면에서 실패했다. 코드는 실물에서 숫자 몇 개를 맞춰 고칠 수 있다.
- 위치는 천장 카메라: 바퀴 명령만으로 추정한 방향은 상자 둘레를 돈 뒤 50~150° 틀렸고, 자기 카메라로는 다른 로봇을 거의 못 찾았다. 소형 로봇 여러 대를 쓰는 연구실이 흔히 쓰는 방식이다(Robotarium 등).
- 공통 규칙(5절)은 몸 움직임의 교착만 풀고 문 순서는 LLM 이 정한다. 순서를 정하는 협업이 계획 결과에 남게 하기 위해서다.

## 3. 단계별

### 접근

둘러보기로 만든 관측 목록에서 계획기가 고른 상자 0.2 m 앞까지 가고, 상자의 넓은 면 정면에 서도록 둘레를 돈다(자세한 것은 [Solo 구조와 모델 3절](solo_architecture.md#3-단계별-설명)). 상자가 로봇이 시작할 때 바라본 방향에서 많이 기울어 있어도, 이동을 마친 뒤 첫 획득은 화면에서 상자를 다시 찾는다. 한 번도 보지 못한 상자는 ACT 에 넘기지 않고 빈손으로 보고한다.

### 집기

ACT 가 화면을 보고 팔과 집게를 움직여 상자를 집어 든다. 집기가 끝났는지는 모델의 done 출력이 아니라 규칙이 판정한다. 바퀴 명령이 0 이고 팔 명령이 든 자세에 가까운 상태가 45행(4.5초) 이어지면 끝난 것으로 본다. 자기가 내보낸 명령 기록만 쓴다([Solo 구조와 모델 3절](solo_architecture.md#3-단계별-설명)).

`ChunkExecutor` 는 학습된 done 이 한 번 나오면 그 상태를 붙잡고(래치) 이후에는 바퀴 0 명령만 낸다. 집기 규칙이 학습된 done 을 무시해도 이 래치가 남아 있으면 로봇이 멈춘다. 2026-11-16 에 규칙이 학습된 done 을 무시할 때 `ChunkExecutor` 의 done 래치도 함께 풀도록 고쳤다. 그래서 로봇이 멈춰 서지 않는다.

### 들었는지 확인

들고 나서 0.4 m 물러나 앞 바닥을 보고, 집었던 자리(천장 카메라 자세로 계산)도 돌아본다. 그 자리에 같은 색 상자가 남아 있으면 빈손으로 보고하고, 계획기에 알린 뒤 다시 둘러보고 다시 고른다(한 번까지). 화면 아래에 든 상자가 보이는지만으로는 가를 수 없었다. 어느 색을 들었는지는 로봇이 자기 목록에서 고른 항목의 색이고, 평가 쪽 정답과 맞춰 본 값은 쓰지 않는다.

### 운반과 목적지 표식 찾기

문으로 가서 지나가고, 계획기가 고른 벽의 번호 표식을 찾아 그 앞에 선다. 자기 위치는 천장 카메라 측정값을 쓴다. 표식의 위치는 방향은 자기 카메라 화면에서, 거리와 표식이 향한 쪽은 그 시선이 닿는 벽(주어진 경기장 모양)에서 얻는다. 문에서 3~4 m 비스듬히 읽으면 거리가 0.5 m 까지 틀렸다. 가까이서 다시 못 보면 25° 간격으로 좌우를 훑는다.

### 문 통과

경기장을 알 때는 주어진 벽과 지금 잰 로봇 위치만 쓰고, 예전에 자기 카메라로 본 점(지금은 없는 것)은 쓰지 않는다. 지도 층과 사라지는 장애물 층을 나누는 Nav2 costmap 방식을 따랐다.

### 내려놓기

정해진 순서(전진, 팔 내림, 집게 열기, 후진)를 재생한다. 교사 시연 140개에서 뽑은 87행 고정 순서다. 목적지 표식 앞에서 놓거나, 계획기가 "내려놓고 끝내기"를 골랐을 때는 그 자리에서 놓는다. 내려놓은 뒤 그 로봇의 실행이 끝난다.

## 4. 위치와 정보의 경계

| | 실행층(코드, ACT) | 계획층(LLM) |
|---|---|---|
| 자기 위치와 방향 | 천장 카메라 측정값(0.5초마다) | 방 이름만 |
| 다른 로봇의 위치 | 천장 카메라 측정값. 경로를 고를 때 피하고, 옮기는 중 바로 앞에 있으면 멈춘다 | 받지 않는다 |
| 벽, 문 | 고정 정보로 받는다 | 받지 않는다 |
| 목적지 표식의 위치 | 받지 않는다. 자기 카메라로 번호를 읽어 찾는다 | 받지 않는다 |
| 상자 | 자기 카메라 | 자기 카메라로 본 목록 |

경기장 모양(벽, 문)은 실행층에 준다. 문을 자기 카메라로 찾다가 실패하는 일이 가장 많았기 때문이다. 상자의 실제 위치, 목적지 표식의 위치, 접촉력은 어느 층에도 주지 않고 채점에만 쓴다. 시뮬레이션도 천장 카메라 화면을 그려서 실물과 같은 방법(번호 표식 읽기)으로 위치를 낸다.

### 실물 관측 연결

| 실행층 입력 | ras1에서 확보한 관측 | 현재 코드 연결 |
|---|---|---|
| 자기 카메라 | 고정 팔 자세의 640×480 영상. 왜곡 보정 뒤 초록 벽 밑 접점과 회색 바닥 특징점을 읽음 | `run_wall_distance.py --place-memory`가 정지 관측마다 `Ras1PlaceObservations`를 호출 |
| 지역 위치 | 연속 관측의 바닥 특징점 정합으로 상대 이동과 회전 추정 | 설계 카메라 높이와 장착 오프셋으로 첫 차체 기준의 `x, y, yaw` 산출. 추적 실패 시 새 위치는 비움 |
| 관측된 벽 | 그 시점에 보이는 초록 벽·바닥 접점 | `PlaceMemory.observe_wall_contacts`가 기존 5cm 기억 격자에 저장. `CarryNav`의 지역 경로가 이 벽 점을 읽음 |

11월 12일 ras1에서 카메라를 고정하고 차체를 실제로 왕복시켰다. 영상에서 추정한 벽 거리는 설계 환산으로 17.6 → 22.8 → 17.4cm였다. 저장된 6개 관측을 실행층의 장소 기억에 재생해 벽 점이 들어가는 것을 확인했다. 관측 위치는 첫 차체 기준이다. 경기장 좌표와의 정합, 실제 거리 정확도, 들고 이동할 때의 카메라 자세와 문 통과는 검증이 남아 있다. [실물 실행과 재생 방법](../experiments/2026-11-12-green-wall/README.md#실물-관측을-현재-운반-실행층에-연결)

## 5. 로봇 사이 공통 규칙

모든 팀 구조에 같다. LLM 이 정하는 것(어느 상자, 어느 표식, 문을 지금 지날지)은 그대로 두고, 그 사이의 몸 움직임에서 생기는 교착만 고정 규칙으로 푼다. 통신 없음(T0)에도 똑같이 적용되고, 로봇끼리 예약이나 협상을 하지 않는다. 다른 로봇의 위치는 천장 카메라로 실행층만 안다.

| 상황 | 규칙 |
|---|---|
| 상자로 다가가는 중 | 번호가 더 낮은 로봇이 앞 1 m(좌우 0.45 m) 안에 있으면 번호가 높은 로봇이 멈춰 기다린다(한 번 접근에 최대 20초). 서로 먼 상자로 가다 가운데서 길을 막아 빈 바닥을 집던 문제 때문이다 |
| 들고 옮기는 중 | 다른 로봇이 앞 0.75 m 안에 있으면 멈춘다 |
| 문 앞·문 너머에 다른 로봇 | 2초 기다렸다 다시 본다(최대 20번). 지나가는 로봇 때문에 바로 포기하던 문제 때문이다 |
| 목적지를 고르기 전 | 번호가 높은 로봇은 상자를 든 뒤 4초(메시지 지연 2초의 두 배) 들은 다음 고른다. 두 로봇이 거의 동시에 들면 상대의 메시지가 결정 뒤에 도착했다(사용자 결정 2026-11-15) |
| 메시지 | 보낸 뒤 2초 뒤에 도착한다. 상한과 이동 중 기회는 [계획기와 메시지 규칙 4절](planning_messages.md#4-메시지-규칙) |

## 6. 기록 정정

- **놓기의 완료 원인.** 요약의 "learned done bit 로만 완료" 노트는 놓기가 고정 순서표로 끝나는 경우에 틀리다. 그 실행에서는 `release_code_v1` 이 표의 마지막(87번째) 행에 달린 done 표시를 내고, 집기 규칙을 켠 실행에서 `SoloSequence` 가 완료 원인을 적을 때 이 값도 학습된 done 과 같은 이름('done')으로 들어간다. `SoloSequence` 의 설명문도 놓기가 학습된 done 으로 끝난다고 적었다. 집기가 규칙으로 끝난 경우만 'rule' 로 따로 남는다. 놓기가 표로 끝났는지는 실행 보고의 `release_code_v1` 항목(`table_done`)으로 읽는다.
- **`InputAudit` 의 0.** `harness/grasp_act_rollout.py` 의 `InputAudit` 는 기록의 `teacher_input_fields`, `invisible_measurements`, `held_world_reads`, `top` 을 처음 값 0 에서 바꾸지 않고, 저장소의 실행기도 이 칸들을 고치지 않고 보고에 그대로 싣는다. `accept` 가 세는 것은 허용 목록 검사에 걸린 입력(`forbidden_input_fields`)과 요청 수(`requests`)뿐이다. 따라서 앞의 네 칸의 0 은 센 결과가 아니라 초기값이고, 정답 입력을 읽지 않았다는 측정으로 쓰지 않는다.
